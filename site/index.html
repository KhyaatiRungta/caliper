Agent evaluation harness

Know whether your agent got better, or just different.

Caliper runs a task suite against your agent, scores the whole trajectory rather than the last line of output, and diffs two versions. When a task that used to pass stops passing, it exits non-zero and blocks the merge.

Overview

Most people build agents. Few measure them.

Almost every agent eval compares a final answer to an expected string. That measurement is cheap, obvious, and blind to most of what goes wrong in production.

An agent that answers correctly after nine tool calls, two of them identical and one of them a crash it papered over, scores exactly the same as one that answered in three. The first is three times the bill, three times the tail latency, and one traffic spike away from an incident. The score says they are the same agent.

The gap shows up at the worst moment. Someone edits a system prompt on a Friday, the suite still reports 84%, and cost per conversation quietly doubles because the model started double-checking itself. Nothing in the harness was looking at the trajectory, so nothing in the harness could have said so.

Fails the build on regressions

Run caliper compare a b --fail-on-regression as a CI step. It exits 1 when a named task goes from pass to fail, and 0 otherwise. Infrastructure errors are excluded in both directions, so a rate limit never blocks a merge.

Scores the whole trajectory

Seven trajectory graders read the step list, not the final string: step efficiency, tool choice, redundant calls, error recovery, and cost and latency budgets. They catch the regressions a final-answer check structurally cannot see.

Works on the agent you already have

The entire coupling is one method: run(task) -> Trajectory. No base class, no framework, no patching of your LLM client. Roughly ten lines of recording makes a hand-written loop measurable.

How it works

Suite in, trajectory out, regression gate at the end.

  1. 01

    Load the suite

    YAML parses into Task objects. Defaults merge into each task, and a duplicate id is a hard error, because a silently dropped task is a silently missing regression.

  2. 02

    Resolve the agent

    --agent reference-v2 goes through the registry; --agent mypkg.adapter:build resolves anything importable. The adapter's version is the axis the whole comparison is built around.

  3. 03

    Dispatch in parallel

    A thread pool, four workers by default. Each task carries its own timeout, enforced over execution time only, so a task queued behind three others is not penalised for waiting its turn.

  4. 04

    The agent records steps

    Each step carries a kind, a name, input and output, tokens, cost, latency, and an error string if it failed. The recorder captures an exception into step.error before re-raising, so an agent that dies mid-tool still leaves an accurate record of the tool that killed it.

  5. 05

    Isolate failures

    A task that raises produces a failing result and nothing else. A transient provider fault is retried with backoff and, if it persists, recorded as an infrastructure error and excluded from the pass rate. A rate limit is not the agent being wrong.

  6. 06

    Grade

    Graders are pure functions, so a stored run can be re-graded later without re-running the agent. A grader that raises yields a failing score carrying the exception, and its siblings still run.

  7. 07

    Persist

    The run is written atomically to .caliper/runs/<run_id>.json in suite order regardless of which worker finished first, so two run files diff cleanly.

  8. 08

    Compare and gate

    Two runs join on task id. Every task is classified pass-to-fail, fail-to-pass, or unchanged, and with --fail-on-regression the command exits 1 if the first bucket is non-empty.

The adapter contract

This is the entire surface an agent must implement. No base class to inherit, no framework to adopt, no callback API to keep up with.

class AgentAdapter(Protocol):
    name: str
    version: str
    def run(self, task: Task) -> Trajectory: ...
from caliper.adapter import TrajectoryRecorder

class MyAgent:
    name = "my-agent"
    version = "v3"

    def run(self, task):
        rec = TrajectoryRecorder(task.id)
        with rec.step("llm", "plan") as s:
            resp = self.client.complete(messages)
            s.output     = resp.text
            s.tokens_in  = resp.usage.prompt_tokens
            s.tokens_out = resp.usage.completion_tokens
            s.cost_usd   = resp.usage.cost_usd
        with rec.step("tool", "search", input=query) as s:
            s.output = self.search(query)
        return rec.finish(final_output=answer)

What is modelled and what is measured. The reference agent is deterministic and makes no LLM calls, so it models the two costs a real agent pays: each step is charged 1450 input and 310 output tokens at published Sonnet-class prices, and sleeps a fixed interval to stand in for network latency. Caliper's measurements of those costs are real, in that the sleep is really slept and the tokens are really summed by the same code path a live agent uses. What is simulated is the agent, not the meter. Against a live agent the same figures come from the provider's reported usage.

Design decisions

What was traded away, and for what.

Adapters, not framework integration

DecisionThe entire coupling between Caliper and an agent is run(task) -> Trajectory. No callbacks, no base class, no patching of the LLM client.

WhyFramework callbacks give you instrumentation for free and then own you. They break when the framework changes, they only cover agents built inside that framework, and they see the framework's idea of a step rather than the author's. A seventy-line recorder that an agent author copies into their own repo survives all of that, and works equally well on a hand-written loop, a remote HTTP service, or a shell script.

CostEvery agent author writes about ten lines of instrumentation, and Caliper cannot see steps the agent chooses not to record. An agent that records nothing is scored on its final answer alone, exactly like every other harness.

Trajectory graders as first-class, not an add-on

DecisionSeven of the thirteen built-in graders read the step list rather than the final output, and a task fails if any of its graders fail.

WhyFinal-answer correctness is a strict subset of what matters. The worked example above shows two agents with identical answers and a 2.5x cost difference; only a trajectory grader separates them. Cost, tool discipline and error recovery decide whether an agent survives contact with production traffic.

CostTrajectory graders need the suite author to supply a reference: a step optimum, an expected tool set, a budget. That is real judgement work, and a badly chosen reference produces a confidently wrong efficiency score. Writing an expected string is much easier, which is part of why most harnesses stop there.

Runs are files, not a database

DecisionEach run is one JSON file under .caliper/runs/, written atomically. The store lists, loads and prunes.

WhyA run is an immutable artifact produced by CI. Files diff in a pull request, attach to a build, commit as a pinned baseline, and copy with scp. A database would buy indexed queries over a dataset that is almost always a few hundred rows, in exchange for a service to run and a schema to migrate.

CostNo indexed queries, and listing a thousand runs reads a thousand files. One module would have to change if that tradeoff ever flipped, which is the point of keeping it in one module.

Regressions exit non-zero

Decisioncaliper compare --fail-on-regression exits 1 when any task went from pass to fail, and 0 otherwise.

WhyA report nobody reads changes nothing; a gate that blocks a merge changes behaviour. Being usable as a CI step is what turns an eval script into infrastructure.

CostThe gate has to be narrow enough to be trusted, so it fires only on a named task that used to pass. It deliberately ignores metrics that moved the wrong way and excludes infrastructure errors in both directions, because a gate that fires on a rate limit is a gate the team learns to bypass. A cost regression with no correctness regression shows in the table but does not block the merge; that call is left to the human reading the diff.

Deterministic ordering under parallel execution

DecisionResults are emitted in suite order regardless of which worker finished first, and task timeouts count execution time only, never time spent queued.

WhyRun files are compared by tools and read by humans. A diff full of reordering noise hides the one line that matters, and a task that times out because it waited behind three slow ones is a bug report about the harness, not about the agent.

CostThe main thread polls futures rather than consuming them as they complete, which is marginally less efficient and is the right trade at this scale.

Limitations

What this does not do.

  • LLM-judge variance is real and is not solved here. Re-grading the same response can land in a different bucket, especially near the boundary between "correct with a minor flaw" and "partially correct". Temperature 0, a fixed five-point rubric with named anchors, and majority vote over n samples with the agreement reported in the score detail all reduce it. None of them eliminate it. A comparison that hinges entirely on a few points of llm_judge delta hinges on noise, and the deterministic graders should carry the weight wherever a task admits one.
  • No distributed execution. One process, one thread pool, one machine. Adequate for a suite of a few hundred tasks and not a replacement for a job queue. A suite that takes an hour on one box will take an hour.
  • Timed-out tasks are abandoned, not killed. Python cannot safely kill a thread. The result is recorded as a timeout immediately and the run proceeds, but the worker may still be running underneath and still holding whatever resource it held. This is the correct trade for an eval harness and the wrong one for a scheduler.
  • No live dashboard. Plain text to stderr during a run and a static HTML report afterwards. Deliberate, but it means no streaming view of a long run beyond the progress lines, and no way to watch a single trajectory unfold.
  • A task suite is only as good as its author. Caliper measures what it is told to measure. Step optima and expected tool sets are human judgements about what a correct trajectory looks like, and a suite that encodes a bad assumption will report that assumption back with total confidence. The harness cannot tell you your suite is wrong.
  • Cost figures depend on the provider's reported usage. Where OpenRouter returns usage accounting, Caliper uses it. Where it does not, Caliper falls back to a per-model price table that will drift out of date, and prints no warning when it does. Treat absolute dollar figures as indicative and relative ones as sound.
  • The built-in reference agent is a fixture. It is deterministic and rule-based and makes no LLM calls. Its two versions differ in routing policy, which stands in for a prompt change and produces the same class of trajectory difference. The measurements are real; the thing being measured is a stand-in, and a real agent will be noisier across repeated runs than this one is.

Running it locally

Clone it and the benchmark reproduces.

bash
$ git clone https://github.com/Manavarya09/caliper && cd caliper
$ python3.11 -m venv .venv && source .venv/bin/activate
$ pip install -r requirements.txt
$ pip install -e .                      # optional, puts caliper on PATH

# Reproduce the table above. No API key needed.
$ caliper run suites/reference.yaml --agent reference-v1 --offline
$ caliper run suites/reference.yaml --agent reference-v2 --offline
$ caliper compare latest latest~1

# As a CI gate. Exits 1 if any task went pass -> fail.
$ caliper compare latest latest~1 --fail-on-regression

# Inspect one trajectory step by step, or export an HTML report.
$ caliper trace latest add_two_numbers
$ caliper report latest --against latest~1 --html report.html

# 269 tests, all passing with no API key.
$ pytest

Only the llm_judge grader and live agent runs need credentials:

bash
$ export OPENROUTER_API_KEY=sk-or-...    # or put it in .env
$ caliper run suites/strata.yaml --agent strata

The suites for the two sibling agent projects, suites/strata.yaml and suites/quarry.yaml, import their adapters lazily. If the sibling repository is not on the import path the run fails with instructions for getting it there, and points you back at the reference agent in the meantime.
